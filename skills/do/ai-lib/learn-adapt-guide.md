# Learn / Adapt — the candidate procedure

The buckets, gates, Inventory rule and push cap live in
[capture-doctrine.md](../source-notes/capture-doctrine.md), which is binding. Read that
first. This file holds the procedure for generating candidates and the worked passes and
fails, which is where the judgment actually lives.

### Step 1 — Inventory the candidates

After writing the distilled body, list every discrete claim, framework, phrase, tactic,
diagnostic, or data point. **Do not bucket yet.** For a 3,000-word source, 15-30 candidates
is normal.

### Step 2 — Filter: is it Learn/Adapt material at all?

**Keep** if it satisfies at least one:
- A named framework, tactic, principle, diagnostic, or memorable phrase.
- It could change how you act in a **live** project — verified against the project folder,
  never against a remembered list — or in a real artifact: a post, a workshop, an onboarding
  doc, a coaching session, a skill.
- A verbatim pull-quote with independent punch.

**Discard to Inventory** if:
- It is background context ("there are four model versions", "MCP stands for..."). That
  belongs in the body.
- It paraphrases something you already know — cross-check the index and your own principles.
- It is a claim with no actionable edge: "AI will change work."

### Step 3 — Route through the gates

Each survivor goes through the three buckets. Exactly one, or Inventory.

**Teach — passes:** *"A project workspace can now hold a file that every chat inside it reads
automatically. Someone drops their team's tone-of-voice doc in once and stops pasting it into
every draft request."* Non-technical, tools they already have, teachable in a live room.

**Teach — fails:** *"This repo orchestrates sub-agents over stdio."* Needs a command line and
a repo → Inventory. This is the shape of material that gets rejected wholesale by an
audience: technically interesting, unusable by them.

**Adapt — passes:** *"Step 3 of the publishing SOP has you re-reading each draft hunting for
the same five voice violations; writing those five down as checkable rules moves the job to
`/fact-check`. Switch cost: one afternoon."* Names the step, says what is worse, states the cost.

**Adapt — fails:** *"You could use this to work more efficiently."* No named current way, so
it is not an Adapt idea.

**Write — passes:** *"The reframe 'they're not resisting you, they're protecting something' —
the exact move the chapter on stakeholder pushback needs to open with."* Binds to a live
section, and it is a line rather than a concept.

**Write — fails:** *"Psychological safety matters for teams."* A concept, bound to nothing.

### Step 4 — Anti-fabrication

Every idea traces back to specific lines in the source. If it is your extrapolation, it is
not the source's idea — Inventory it.

### Step 5 — Blank beats wrong

An empty bucket loses its heading. **Never pad.** One strong idea beats one strong plus three
filler, and zero across all three buckets is a legitimate result.

### Step 6 — Strip the flattery

Before shipping, cut: sycophancy ("interesting", "thought-provoking", "a good start"), hedges
("may be worth considering", "could potentially" — say it directly or cut it), and anything
that overlaps what your principles file or a recent entry already says.

### Step 7 — Order within each bucket

Highest-leverage first: what could ship this week, not what is most abstract.

### Step 8 — When to skip the section entirely

Write **"N/A — reference material"** for the whole Learn / Adapt section only when the source
is a pure spec, changelog, or set of docs with no argument, or a data dump with no claims to
adapt. The `## Inventory` section is still written either way.
